Evidence: scratch/camerapair_chapter45_outdoor_wide_20260814, oracle winner f5737, strict static-world camera match 0.17 thresholds, UI longest-run shape 1/1, front buffer 0.8239 = 1.7 console frames of drift. Scene color 0.8254 vs self 0.8012 and scene depth 0.9579 vs self 0.9160 rule out a global viewpoint or base-pass failure. At native draw 2089 the first srcD5A0 f22 atlas is 96.36% far depth, mean 0.9830; oracle copy361 is 87.77% far, mean 0.9322. Visual decode shows four corresponding atlas quadrants but native caster silhouettes occupy much less of each tile. The following srcC2D0 f6 pass is also deficient (0.3610 vs self 0.6774). Native issues 8 D5A0 resolves while oracle issues 9, so ordinal alignment of later atlas copies is structurally unsafe, but this first full 864x864 copy is independently named and decodable. Previous Act-1 C051 scored its atlas above 0.99; this scene falsifies its universal expiry condition and proves coverage was scene-specific.

The four leading atlas draws are now joined by vertex count rather than ordinal. Three of them carry the same load-bearing c230..c237 light/projection rows on both guests (10,932 and 8,154 exactly; 5,814 differs by one float ULP in two translation components). Their assembled/survived-clip/fragment-invocation counts are respectively 3644/1829/59379 exactly on both sides, 2718/1373/16664 exactly, and 1938/1011/33281 oracle versus 1938/1011/33287 native. The 8,448-vertex draw has genuinely different c230..c241 and is a separate title-state/geometry divergence. Equal fragment invocations do NOT establish equal unique pixel coverage: the matched 10,932 tile stores 31,618 non-clear oracle pixels but only 13,491 native pixels.

The D24S8 resolve is ruled out as the source. `scratch/ch45_live_depth_valid_20260814` dumps native's live D32 depth after every matching shadow-depth draw. Its tile quantiles and means reproduce the first resolved atlas to 8-bit quantisation (for the 10,932 tile, live mean 0.96384335 and resolved mean 0.9638444). Therefore the loss exists while rasterising/testing the shadow draw, before the resolve shader reads or encodes depth. Next discriminator: capture/compare vertex-shader output positions or an equivalent per-primitive spatial distribution for the three matrix-matched draws, then distinguish wrong fetched/skinned vertices from wrong depth-test evolution. Aggregate pipeline statistics cannot make that distinction.

The complete guest inputs and translated programs are now ruled out for the four leading draws. `scratch/camerapair_chapter45_geometry_20260814` hashes each complete raw index buffer and VS fetch range on both guests; all eight hashes match exactly. The relevant system transform words, pixel c0/c1/c255, texture fetch description, and the complete 8,192-byte tiled DXT1 source hash also match. `scratch/camerapair_chapter45_spirv_20260814` adds the actual translated modules: VS is 38,080 bytes / `54D380A888BFA9DD` and PS is 14,016 bytes / `7FF5D54B2EF71B6B` on both renderers. The PS has no kill: it samples the texture and writes `oDepth` on every invocation. `scratch/camerapair_chapter45_sampler_20260814` found one genuine host-state omission: the oracle requests 4x anisotropy while native decoded 4x but did not put it in `VkSamplerCreateInfo`. Native now enables and caps anisotropy through the shared device-feature path. That correction is not this issue's root cause: the full 45-frame validation `scratch/camerapair_chapter45_aniso_20260814` still has first-atlas mean 0.9830 native versus 0.9322 oracle.

The actual uploaded BC1 payload is also ruled out, with a discriminator on each shipping path rather than another decode beside it. The Xenia fork copies the selected texture-load compute shader's output only after the compute-to-transfer barrier; native hashes `DecodeGuestTexture(..., true)`'s actual upload vector. Both produce 32 canonical bytes with FNV-1a `683FAB1B2803B4D0` for guest base `0x1666F000`. The oracle negative scanned 18,822 texture loads and matched zero when given an absent base. An earlier oracle probe placed the copy before Xenia's barrier and returned the plausible but false hash `6B26C291000C33CA`; that result is invalid and is the reason the barrier placement is part of the instrument's contract.

The longer paired window `scratch/camerapair_chapter45_palette_20260814` falsifies two more proposed causes. Oracle's first full atlas is byte-identical throughout frames 5901..5927, so this is not a temporal or animation-phase mismatch. For the comparable 5,814-, 8,154-, and 10,932-index casters, every c0..c7 and c230..c237 word actually read by VS `8354E5CC00C0A98C` matches except for two one-ULP translation words in the 5,814 draw. Its complete bone palette c0..c229 is exact; the other two palettes differ only at float noise (maximum `2.29e-6`). The differing whole 4,096-byte UBO hashes were dominated by c238+ state that this microcode never reads, and therefore did not establish a load-bearing input difference. The 8,448 draw remains a genuinely different title-state draw and must not be used to generalise the three matched casters.

Guest-to-host SSBO visibility is also not an open flush hypothesis. Native allocates the 512 MiB guest mirror only from a Vulkan memory type containing both `HOST_VISIBLE` and `HOST_COHERENT`, then copies every page-coalesced fetch range before queue submission. A non-coherent-memory flush cannot explain the result. Because both renderers additionally execute byte-identical translated VS/PS modules with the matched fetched bytes and load-bearing constants, the next discriminator must be at the host raster/interpolation boundary: compare the exact Vulkan viewport/scissor, primitive assembly/restart, and interpolated texture-coordinate/sample result for one matched primitive that covers an oracle-only pixel. A generic post-VS CPU re-execution over the same guest inputs would only restate the already-proven inputs and is not sufficient.

Xenia's polygon offset was missing natively and was implemented using `GetPreferredFacePolygonOffset` plus Xenia's exact D24/float24 and subpixel scaling. The paired `bias` versus `nobias` control changed only two pixels in the first atlas (MAE `0.00055`) and left the deficient silhouettes unchanged. Polygon offset is therefore a real parity omission but is falsified as issue 109's cause; it must not be presented as this fix.

`scratch/camerapair_chapter45_raster_20260814` compares host raster state directly. The matched 10,932- and 8,154-index casters use byte-identical Vulkan viewport, z range, scissor, triangle-list initiator and `PA_SU_SC_MODE_CNTL` on both sides. The 5,814 and 8,448 draws exchange atlas quadrants because their title state/order differs, as already observed; they must be compared by draw identity rather than tile. The pair's moving-frame score lies outside the short console self-curve, but the exact per-draw state comparison is independently valid because it is joined by shader and vertex count.

Processed index endianness is also falsified for these casters. Capture had a real general bug: it discarded `VGT_DMA_SIZE.swap_mode`, and native unconditionally byte-swapped every index. The data model and preparation path now preserve and implement all four modes, with compile-time vectors covering both changed and unchanged answers. However `scratch/camerapair_chapter45_indexfix_20260814` positively records endian mode 1 for all four selected shadow draws, the mode for which the old byte swap was already correct. This correction therefore does not explain issue 109 and must be evaluated as a separate parity fix.

The opacity-sampling boundary is now isolated by `scratch/ch45_white_texture_20260814`. This exact-camera run accepted the validated 27-step input route and used the existing `GEARS_DRAW_NOTEX` control, which serves the backend's 1x1 white texture for guest bindings. The 10,932-index tile then writes exactly 31,618 non-clear pixels, identical to oracle and up from normal native's 13,491. The 8,154-index tile writes exactly 12,147, also identical to oracle and up from 5,884. Their depth means are correspondingly close (white native 0.90258/0.96839 versus oracle 0.89791/0.96687). Thus post-VS geometry, primitive assembly, viewport/scissor, clipping and potential raster coverage are exonerated for both same-tile casters. The loss is entirely which normal guest-texture samples fall below the PS's 0.5 opacity threshold. Next discriminator: capture the sampled coordinate and returned value for one oracle-only pixel, then compare guest-swizzle/view composition and normalized-coordinate handling. Do not re-derive geometry, index endian, depth resolve, depth bias, or animation timing.

Host D24 attachment precision is independently falsified. A format-aware native control used `VK_FORMAT_D24_UNORM_S8_UINT` for guest kD24S8, matching Xenia on this GPU, while retaining D32 float for kD24FS8. `scratch/camerapair_chapter45_d24_20260814` still gives the first atlas mean 0.9830 native versus 0.9322 oracle, including entirely clear native regions inside the top-left 422x422 tile. The control change was removed rather than landed. This pair's whole-frame score lies outside its console self-curve, so it proves only the independently structured first-atlas negative, not a final-frame regression. The remaining discriminator is spatial post-VS/raster output: localise which primitives cover the oracle-only pixels, then capture their post-VS positions/depths. Re-checking guest bytes, texture upload, constants, sampler state, SPIR-V, resolve encoding, or host depth precision is re-derivation.
