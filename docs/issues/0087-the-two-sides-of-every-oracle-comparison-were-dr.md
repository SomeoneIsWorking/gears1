tools/oracle_lockstep.sh is built on the right idea and its header states it
correctly: both emulators count the guest's own VdSwap boundary, so indexing by
that counter makes frame N the same game moment on both sides. What it actually
did was feed the two sides two hand-written strings that were not the same walk.

    ours    f150:START, then A at f300,420,540,660,780,900,1020,1140,1260
    theirs  START@150 REPEATING EVERY 270 FRAMES, A@300 REPEATING EVERY 120

Our side stops pressing at f1260. The oracle's repeats never stop: it goes on
pressing START -- which is PAUSE once the level is up -- and A every 120 frames
for the whole run. Neither side has any movement input, so neither walks
anywhere deliberately. Two runs driven that differently are at different points
in the game at every gameplay frame, which is precisely the property the script
exists to provide.

The cost is not hypothetical. Two findings were built on comparisons made this
way and both are now withdrawn:

  * #86, "our Act 1 scene is rendered inset" -- the two frames were at different
    camera positions, and our side's "border" was rendered-but-dark geometry.
  * C023, "eight pixel shaders the console binds and we never do" -- a set
    difference over two runs that reached different points in the game measures
    how far each got. The oracle's frame 6000 has Marcus carrying a Lancer with
    312 rounds; ours is still in the unarmed prologue, which is the whole of the
    "missing HUD" that was read as evidence.

FIX. The walk is now a TABLE, in tools/menu_walk.sh, once:

    GEARS_WALK_TABLE="750:START 900:A 1050:B ... 4500:LY+ 5100:LY0 ..."

with `gears_walk_ours` and `gears_walk_theirs` GENERATING the two notations from
it, so they cannot drift again without the table changing. It is frame-keyed
because a level load stalls the frame counter on both sides while the wall clock
runs on, and it includes stick deflections so both sides actually walk.
oracle_lockstep.sh cross-checks that every frame the table names appears in both
generated strings, and PROVES that check fires on a deliberately mismatched pair
before trusting it to pass -- the first version of the check compared token
counts and flagged the correct walk as a mismatch, which is exactly the failure
mode a guard that is never exercised has.

### Note (2026-08-12)
THE WALKS NO LONGER HAVE TO MATCH. This entry is a real tooling defect and its diagnosis is correct -- the two sides were fed different input schedules, so frame N was never the same game moment. But the requirement it exists to enforce, that both sides be driven identically so their frames correspond, is no longer the only way to make a comparison. Matching on the VIEW-PROJECTION does it directly: it is guest data both emulators carry, so two frames carrying the same one are the same moment regardless of how either side got there, and the two runs may be driven completely differently or not driven at all. GEARS_DRAW_FRAME_CAMERA and tools/camera_match.py implement it and are validated in both directions. THE PROOF THAT THIS IS ENOUGH is that a camera-gated capture and an oracle run with no shared schedule resolved THE SAME 16 PASSES with none only-ours and none only-theirs -- the first paired capture to achieve that -- where every content-predicate capture before it reported structural mismatches that were really two different moments. Fixing the walk mismatch is still worth doing for any purpose that needs the two sides to follow the same route, but it is no longer a prerequisite for comparing them.

### Note (2026-08-12)
MY OWN SCRIPT WAS KILLING THE CONSOLE AT THE START OF ITS DUMP WINDOW, WHICH IS WHY THE PREVIOUS RUN'S PEAK WAS AT THE WINDOW EDGE. tools/camera_pair.sh waited for the vertex-constants file to appear and then stopped the oracle five seconds later. Those constants land on the FIRST dumped frame, so the console was always terminated at the very beginning of its window: asking for GEARS_ORACLE_DUMP_FRAMES=45 produced 4 front-buffer frames, and the earlier run's 5. The 'widen the window' fix I proposed could not have worked, and the parameter looked as though it were being ignored. MEASURED: with DUMP_FRAMES=45 the console dumped 86 files, 4 of them front buffers. FIXED: the wait now counts the front-buffer dumps -- one per dumped frame -- against the requested count, prints progress every 60 s, and when it falls short says so AND says what a short window does to the reading ('a BOUNDARY peak in the scores means the window still did not span our moment'). The previous behaviour had no way to report that it had cut the window short, which is why it read as a parameter that did nothing. THIS ALSO EXPLAINS THE BOUNDARY PEAK cleanly and removes the alternative reading: the console's window was four frames near its own gameplay start while our camera gate held 273 frames, so the two never overlapped and the best console frame was necessarily outside the window. Nothing here says anything about whether the camera gate is a sufficient pairing key -- that question is still untested, and 0.296 remains a lower bound rather than the gate's score.

### Note (2026-08-12)
ROOT CAUSE OF THE CAMERA GATE'S WEAKNESS, FOUND STATICALLY: ITS METRIC CANNOT CONSTRAIN ORIENTATION AT ALL. The gate computes d = max over the 16 components of |ours - theirs| and compares it to one threshold. But the view-projection's rows differ by THREE ORDERS OF MAGNITUDE. From the frozen camera of the run that scored 0.376 (scratch/camerapair/ours/camera.txt, shader F3E9368C1BB68ECC at guest frame 793): c230=(-0.962084, 0.187028, 0.251394, 0.251646), c231=(-0.0043975, -1.65064, 0.370979, 0.371351), c232=(0.272716, 0.633181, 0.892847, 0.893741), c233=(35.7629, 757.384, -415.085, -405.501). The three rotation/scale rows are bounded by about 1.65 in absolute value; the translation row reaches 757. CONSEQUENCE: at a threshold of 10, the largest difference the rotation rows can PHYSICALLY produce -- a complete sign flip of a 1.65 component, i.e. the camera turned right around -- is 3.3, which is under the threshold. So no rotation difference whatsoever can fail this gate. The threshold binds only on the translation row, and there only to +/-10 out of ~757, about 1.3%. THE GATE MATCHES POSITION LOOSELY AND ORIENTATION NOT AT ALL, which is a complete explanation for 'CAMERA MATCHED at 9.29' next to a picture correlation of 0.376. AND NO SINGLE THRESHOLD CAN FIX IT, which is why this is a metric defect rather than a tuning one: constraining orientation needs a threshold around 0.05 (a degree of rotation moves a unit-vector component by about 0.017), and the translation row can never satisfy 0.05 when its components are in the hundreds. The two requirements are three orders of magnitude apart and the metric offers one number. FALSIFIABLE PREDICTION, MADE BEFORE THE RESULT LANDS: the CAMERA_NEAR=2 run now in flight will NOT materially improve on 0.376, because a threshold of 2 still cannot fail any rotation (max possible rotation contribution 3.3, and typical differences far below 2). If it does improve materially, this analysis is wrong and the metric is merely loose rather than blind to orientation. THE FIX IS TO COMPARE THE MATRICES BY WHAT THEY DO, not by their coefficients: transform a fixed set of world points through both and compare the resulting SCREEN positions in pixels. One threshold in pixels then constrains position and orientation together, in the units the comparison actually cares about, and it is interpretable -- 'the two cameras put the same world point within N pixels of each other'.

### Note (2026-08-12)
TIGHTENING THE OLD SCALAR THRESHOLD BUYS NO PAIRING AT ALL, NOT A BETTER ONE. Ran the knob sweep the previous note called for: CAMERA_NEAR=2 against the 10 that produced 0.376. IT NEVER MATCHED -- 16,140 frames held, closest approach 2.43, and the log plateaued at 1187.26 for the last several thousand frames, i.e. the guest walked past that viewpoint early and never came back near it. No capture, no score. SO THE PREDICTION I RECORDED IS UNTESTED, NOT CONFIRMED. I predicted CAMERA_NEAR=2 would fail to improve on 0.376 because the metric is blind to orientation; the run cannot speak to that, because it produced no measurement at all. Do not read it as support. WHAT IT DOES ESTABLISH is a practical bound that was not known: a threshold of 10 is already near the limit of what this level's camera motion allows, so the old metric has no headroom. Tightening it does not trade coverage for accuracy, it eliminates the match. AND IT CAUGHT A DEFECT IN MY OWN FIX BEFORE IT COST A RUN. The new separated metric defaulted to a translation tolerance of 0.002 of the row's magnitude, which is 0.002 x 757 = 1.51 absolute -- TIGHTER than the 2 just shown unreachable. It would have reproduced this same no-match. The default is now 0.013, i.e. about 10 absolute, the value the level demonstrably permits. THE DESIGN FOLLOWS FROM THAT: position stays at the tolerance the motion allows, and ALL the added discrimination comes from the rotation limit, which the old metric did not constrain at all rather than constraining loosely. That is the whole point of separating the two -- there was never a scalar that could do both, and the evidence now shows there is no room to tighten the one it did constrain.

### Resolution (2026-08-13)
THE INITIAL-STATE SPLIT WAS NOT AN INPUT-TIMING PROBLEM. Native's XamShowDeviceSelectorUI selected PC storage and completed its overlapped, but xam_notify.cpp kept every listener permanently empty. Xenia broadcasts XN_SYS_UI=true before completion and false 200 ms afterward; Gears keeps its own NO STORAGE DEVICE modal up until that close notification. Implemented real area/version-filtered listener queues and the selector's open/completion/delayed-close sequence. The shipping test drives delivery, delay, exactly-once consumption and a live-only listener that MUST reject the system event. The real discriminator is visual: before the selector response frame 740 carries the modal; after the fixed selector frame 550 carries the same Ashes scene with the modal gone and CHECKPOINT visible.

With that upstream split fixed, the f6150 walk was unnecessary. A two-event route -- f450 START, f600 A -- reconciles both boot states. scratch/camerapair_short_ui_20260813 passes every gate: matching provenance/camera digest, both input arms fired, camera match 0.61 thresholds, decoded buffers show the same door with no overlay, and score 0.7496 against oracle f901 = 1.1 frames on the console's curve (limit 3.0). camera_pair.sh now defaults to this route. This broad issue stays open because old comparisons cannot be retroactively repaired, but equal-state capture is no longer blocked.
