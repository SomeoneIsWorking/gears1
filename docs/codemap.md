# Codemap

Orientation map for gears1. Consult this **before** starting work to find where
a subsystem lives and how far it actually got; update it in the **same commit**
that lands or changes a subsystem.

Status vocabulary — deliberately narrow, so it cannot flatter the project:

| Status | Meaning |
|---|---|
| **real** | Implemented and verified against real data. Does what its name says. |
| **partial** | Genuinely implemented, but with known gaps. Gaps named. |
| **null** | Deliberately does nothing while presenting a working interface. Not a stub to be filled in later by accident — a *documented* absence. |
| **absent** | Not implemented. Traps loudly if called. |

## Where things are

| Path | What it is |
|---|---|
| `config/gears.toml` | XenonRecomp configuration: XEX path, save/restore helper addresses, switch-table file |
| `tools/gdf_extract.py` | GDF/XDVDFS disc reader. `--list`, `--extract`, `--extract-all` (resumable) |
| `tools/xex_probe/` | XEX decrypt/decompress, section + import dump, save/restore helper byte-scan |
| `tools/dedupe_recomp.py` | Removes duplicate/stale generated TUs. `--check` in CI: duplicate `__imp__sub_X` definitions make the link order-dependent |
| `tools/prepare_overrides.py` | Strips the weak alias for functions listed in `runtime/hle_d3d.cpp`, so intra-TU calls reach a native override. **Re-run after changing the override list** |
| `tools/gen_import_stubs.py` | Emits a trapping stub for every import not named in `implemented_imports.h` |
| `extern/XenonRecomp` | Submodule → our fork, branch `gears` |
| `xenia_gpu/` | Build island for Xenia's Xenos microcode front end + SPIR-V back end out of `extern/xenia`. One CMakeLists plus `xenia_host_shim.cpp` — no Xenia sources are copied. Optional at configure time exactly like the Vulkan/SDL3 presenter |
| `tools/shader_extract.py` | Scans any file for `0x102A11tt` shader containers, validates the layout, and writes deduplicated containers. The container layout is documented in its docstring |
| `tools/xenos_translate/` | Offline driver: container (or, with `--raw`, bare captured microcode) → Xenos microcode → SPIR-V + microcode disassembly. Measurement tool, not part of the runtime |
| `tools/system_constants/` | Offline driver: a register-file snapshot (`GEARS_CONST_DUMP` → `scratch/bin/regfile_hotpair.bin`) → the 528-byte `xe_uniform_system_constants` UBO. Ports Xenia's `UpdateSystemConstantValues` (non-FSI) reading our tracked registers; reuses Xenia `draw_util::GetHostViewportInfo` for NDC scale/offset. Verified byte-exact against the bound shader's SPIR-V member offsets. Optional at configure time, links `xenia_gpu` |
| `tools/compare_bound_shaders.py` | Compares runtime-captured microcode against the offline container corpus and ranks the captured set by bind count |
| `runtime/` | The PC-side runtime. See below |
| `tests/` | `test_vmx_instructions` (fork's instruction implementations) and `test_runtime_logic` (kernel object semantics, path translation). Both mutation-checked |
| `tools/decode_bc.py` | Decodes a raw BC1/BC3 blob dumped by `GEARS_DRAW_TEX_DUMP=1` to a PNG. Exists to check the guest-texture **decode** (detiling + endian + block layout) independently of the renderer — if these look like game art, any remaining blackness is downstream |
| `tools/frame_replay/` + `runtime/frame_capture.cpp` | **The renderer's instrument — reach for this before any renderer hypothesis.** `GEARS_DRAW_FRAME_DUMP=<path>` records one frame's whole draw stream (per-draw register snapshots, deduplicated microcode, the non-zero guest pages); `frame_replay <capture>` re-renders it offline in **~550 ms with no guest**. **A capture is not self-contained**: it stores renderer configuration as it was when recorded, and `frame_replay` overrides the guest-memory mirror with the runtime's current value and warns when they differ — a capture from before the mirror was raised replayed with 606 of 722 draws collapsed and produced a plausible, wrong picture (`catalog.py show 57`). Read the **frame geometry reach** line; it warns when any draw fetches past the mirror. Every `GEARS_DRAW_*` knob works, so two arms of a comparison run on **byte-identical input** — which a live run cannot give you, because reaching a gameplay frame costs a 200 s scripted menu walk and each walk lands on a *different* game moment. Validated both ways: byte-identical to the live render of the same frame, and it *changes* when the input does |
| `tools/validate_all.sh` | **Is the renderer still valid Vulkan?** Replays EVERY capture with the validation layer on and fails on any VUID that is not the known point-list PointSize warning. Exists because `frame_hashes.sh` sets no `GEARS_DRAW_*` knob, so the validator never loads in the routine gate — and "validation clean" drifted until it hid seven VUIDs (`catalog.py show 75`, `76`). It runs all 8 captures because the first investigation ran one, act1_v2, which happens to contain no alpha-tested shader and came back clean while five others did not. **Proven to fire**: re-introducing the `demote_to_helper_invocation` over-claim makes it exit 1 and name the captures |
| `tools/verify_present_path.sh` | **Proves the swapchain blit alters nothing, with no window.** Renders exactly one frame, lets the presenter repeat it, captures what reaches the swapchain through `VK_EXT_headless_surface` and compares it byte for byte with the renderer's own readback. PASS means the pixels a person sees are the pixels the renderer drew; it refuses rather than passing when a capture is missing. This closed the one gap every other instrument here has -- they all capture BEFORE the blit (`catalog.py show 60`) |
| `tools/capture_gameplay_frame.sh` | The scripted controller walk from the title screen into Act 1 gameplay (~743 draws, the deferred UE3 pipeline) rather than the title screen (~170 draws, one surface). Use it once to get a capture, then iterate with `frame_replay` |
| `tools/ucode_reduce.py` | **Reduces a title shader's swizzle chains by simulating its register file.** Writing a native pass means restating what a shader computes, and the hard part is the channel rotation — the base-pass material has ten consecutive accumulations each rotating by one, and all of them cancel, which cannot be *seen* from the listing. Applies every instruction to symbolic expressions, interns common subexpressions, prints the straight-line program. **REFUSES** rather than approximating when it meets control flow, predication or an instruction it does not model — a reduction that silently skipped one would read exactly like a correct one. `--selftest` runs seven cases including four negatives, and has already caught two real errors. Every run prints the registers **read before ever being written** — those must all be interpolators, and a computed register appearing there means an instruction was dropped (that is how a bare `mul r9, ...` destination writing nothing was found). `--census DIR` classifies a directory of disassemblies by shape, which is how the base pass was sized: 37 of 61 shaders and 84% of its draws are one family. Validated by reproducing, character for character, the reduction behind `base_pass_lightmap.frag`, which is bit-exact |
| `tools/pass_structure.py` | **Which draws are which UE3 pass.** Reads a `GEARS_DRAW_DIAG` table and attributes every row to a UE3 render phase (clear, prepass, base pass, resolve, occlusion, blended, full-screen), each rule citing the `SceneRendering.cpp` / `BasePassRendering.cpp` line that fixes the state it keys on. This is `docs/native-renderer.md` step 3. It refuses to name what it cannot distinguish: UE3's lights, decals, distortion and translucency share one register state, so they are reported as one `BLENDED` band with that said out loud, and anything no rule matches is printed with its full state rather than dropped. `--selftest` runs the classifier against cases it must accept **and** one it must reject |
| `docs/native-renderer.md` | **The native renderer: design, seam, order of work, and what the first pass cost.** Built against UE3's own sources (`$GEARS_UE3_SRC`, never vendored — licensed). Status: **the renderer no longer emulates the console's EDRAM tiling** (default since 2026-08-05; `GEARS_DRAW_TILED=1` restores it). Six native passes implemented and bit-exact, none merely declared — including three base-pass materials of the same family (of 44 in a frame). The draw emitter is NOT a prerequisite — substitution keys on the pixel-shader hash. Height fog was **withdrawn**: no draw in any capture matches UE3's `RenderFog` |
| `runtime/native_pass.{h,cpp}` + `runtime/shaders/` | **6 passes implemented (all bit-exact), none declared-only. A native pass: our own SPIR-V replacing a title pixel shader**, keyed on the microcode hash, substituted in `gpu_draw.cpp` at module creation. The translated shader is still built, so every pass is A/B'd against it. A roster entry with no module is a *declaration*; `Find()` refuses it and the log distinguishes "on" from "on and none exist" |
| `runtime/spirv_clamp.{h,cpp}` | **Restores the render target's [0,1] clamp that the widened host format loses.** A reinterpreted EDRAM surface gets one float host image, so a fixed-point draw into it blends as if its target were HDR — a translucent UI highlight became a flat saturated slab (`catalog.py show 68`). Inserts an NClamp into the translated SPIR-V for draws whose *guest* format is fixed-point only; part of the shader cache key |
| `tools/gen_native_spv.sh` | `.frag` → SPIR-V → the checked-in C++ header. Modules are generated, not compiled at runtime, so a native pass cannot change under a driver update. **Re-run after editing any shader in `runtime/shaders/`** |
| `tools/verify_native_pass.sh` + `tools/compare_frames.py` | **The acceptance gate for a native pass, in three arms: pixels, INTERFACE and negative control.** The interface arm re-runs under `GEARS_DRAW_VALIDATE=1` and fails on any descriptor/shader-interface warning — two passes here were bit-exact for two sessions while declaring the wrong image view type, which a pixel comparison can never see (`catalog.py show 72`). Renders a capture through both paths and compares pixel for pixel. It deletes the screenshot before each arm (the replay names output by frame number, so a stale file compares a frame against *itself* and reports a perfect match — this happened), refuses rather than passing when an arm produces nothing or both frames are near-black, and runs a second capture as a **negative control** in the same invocation so the comparison is shown able to report a difference |
| `docs/knobs.md` | **Every `GEARS_*` environment variable, in one place.** Add or remove a knob here in the same commit that changes the code. Knobs go through `lucent::config`, never raw `getenv` |
| `tools/catalog.py` + `docs/issues/` | **Findings registry, keyed by symptom. Search it before investigating anything.** `catalog.py search "<symptom>"` |
| `debug_journal/` | Dated narrative of each session. The catalog is the index into it |
| `scratch/` | All derived output, gitignored: `ppc/` generated C++, `game/` extracted disc, `bin/`, `logs/`, `raw/` |

## Runtime subsystems

| Area | Files | Status | Notes |
|---|---|---|---|
| Guest memory | `guest_memory.*` | **real** | 4 GiB sparse window. Physical RAM is one `memfd` aliased at `0x0/0xA0/0xC0/0xE0000000` because guest code converts between them by masking the top 3 bits |
| Heaps | `guest_heap.*` | **works** | Page-granular, honours requested alignment. Address-keyed free list, first fit, coalescing on free; freed pages stay committed but recycled address space is re-zeroed before it is handed out (issue #18). Verified plateau at 192/194 MiB over 25 min of gameplay |
| Image loading | `main.cpp` | **real** | XEX via XenonUtils; refuses an image whose layout differs from the recompiled code's |
| Indirect calls | `guest_memory.cpp` | **real** | 49,475 functions installed into the `PPC_LOOKUP_FUNC` table |
| Variable imports | `import_variables.*` | **real** | 236 resolved. XenonUtils leaves these unresolved upstream; fixed in our fork |
| Threads | `guest_thread.*`, `kernel_thread.cpp` | **real** | Per-thread `PPCContext`/KPCR/TLS/stack. `CREATE_SUSPENDED` is a real gate. Affinity deliberately **not** honoured |
| Sync | `kernel_sync.cpp`, `kernel_spinlock.cpp` | **real** | Critical sections and spin locks are real host locks, correct under real threading |
| Kernel objects | `kernel_objects.*`, `kernel_events.cpp`, `kernel_object_api.cpp`, `kernel_dispatcher.cpp` | **partial**, tested | Events + semaphores, handle table, and guest-memory dispatcher objects bound lazily from their own header. **`ObDereferenceObject` is a no-op** — objects outlive their refcount |
| File I/O | `guest_filesystem.*`, `kernel_file.cpp`, `xam_user.cpp` | **partial** | Real reads from extracted disc files, case-insensitive fallback. **Writes work on save mounts**: the title reports a storage device, creates content, and gets a writable host directory under `$XDG_DATA_HOME/gears1`. No directory enumeration; no save file has landed on disk yet (catalog #45) |
| Memory API | `kernel_memory.cpp` | **partial** | Virtual + physical allocation. Page protection recorded, **not enforced** |
| Time | `kernel_time.cpp` | **real** | 50 MHz Xenon timebase |
| Config | `kernel_config.cpp` | **partial** | Answers only settings with a defensible value; refuses the rest **by name** |
| Strings | `kernel_rtl.cpp` | **partial** | Counted strings, code-page conversion, memory fills. `X_ANSI_STRING` parsing verified |
| Display | `kernel_video.cpp` | **partial** | Reports 1280x720p60 widescreen. Verified that the title's layout does **not** depend on this |
| **Input** | `input.cpp`, `xam_user.cpp` | **real, verified on real data** | `XamInputGetState`/`GetCapabilities`/`SetState` fill the console's own `X_INPUT_STATE`/`X_INPUT_CAPABILITIES`, with the packet number incrementing only on a real change. Three host sources: an **SDL gamepad**, the **keyboard** (Enter=START, Space=A, WASD=left stick, arrows=d-pad), and **`GEARS_INPUT_SCRIPT`** (`"25000:START,25300:"` — timed button states, so a headless run is reproducible). The pad reports connected **only when a source exists**: a connected pad that never changes reads as a player not pressing anything and strands the title at PRESS START. Verified: a scripted START took the title into the **main menu** (`scratch/screenshots/rect/after_start.png`), draws/frame 169 → 178–183 |
| **Player profile** | `user_profile.cpp/.h`, `xam_user.cpp` | **real, tested** | `XamUserReadProfileSettings`/`WriteProfileSettings` over a real store, persisted to `profile.bin` beside the saves. A setting id encodes its own type and 12-bit payload size (`id:16, size:12, type:4`), which is what lets a read buffer be sized without a table of every setting. `X_USER_PROFILE_SETTING` is 40 bytes: id at +16, type at +24, value at +32; `settings_ptr` is a **guest** address. An unset setting reports source `NO_VALUE` and type `UNSET`, because the title must tell "never set" from "set to zero". A short buffer is refused **without writing anything** — a partial result is one the caller cannot detect. `tests/test_user_profile.cpp` |
| **Saved content** | `xam_content.cpp/.h`, `xam_user.cpp` | **real, tested** | Content is a directory beside the player's data; the descriptor handed back is the console's `XCONTENT_DATA` (0x134 bytes, display name UTF-16 at +8, file name in 42 bytes at +0x108). Create/open **dispositions are the console's**: `CREATE_NEW=1, CREATE_ALWAYS=2, OPEN_EXISTING=3, OPEN_ALWAYS=4, TRUNCATE_EXISTING=5` — the title sends flags `0x13`, and having `OPEN_EXISTING=2` meant every open-existing request was answered as a creation. Content **exists when it holds a non-empty file**, not when its directory is present (the runtime creates that directory itself on first write). Enumeration is sorted so two walks agree. `XamContentCreateEx` completes the **XOVERLAPPED** and returns `ERROR_IO_PENDING`: the title branches on 997 and skips the entire load otherwise. `tests/test_xam_content.cpp` |
| **Xam applications** | `xam_apps.cpp/.h`, `xam_notify.cpp` | **real, tested** | `XMsgInProcessCall`/`XMsgStartIORequest` dispatch to the media player (XMP, 0xFA), the gaming service (XGI, 0xFB) and the Live client (XLiveBase, 0xFC). **HANDLED and UNKNOWN stay distinct** so an unimplemented service is still loud rather than buried under a blanket success. Anything needing a Live account fails as `NOT_LOGGED_ON` — a real console answer — rather than succeeding emptily and leaving the title waiting. `XMPGetPlaybackController` writes **through** the two guest pointers in the request, not into the request block. `tests/test_xam_apps.cpp` |
| **Console configuration** | `xconfig.cpp/.h`, `host_time_zone.cpp/.h`, `kernel_config.cpp` | **real, tested** | Settings behind **named** identifiers, because a shifted table is invisible: every lookup still succeeds and answers a different question. Language sat at 0x07 where the console uses 0x09, so the title asking for LANGUAGE got the audio-flags entry — 0 where English is 1. The seven time-zone settings (0x01–0x07) are a Win32 `TIME_ZONE_INFORMATION` taken apart, **all four bytes wide**, and the guest's `XapiGetTimeZoneInformation` abandons the whole gather on the first failure — so refusing 0x02 cost the title its entire time zone. Derived from the **host** zone by probing `localtime_r` across the year and bisecting transitions. `tests/test_xconfig.cpp` |
| **Directory listing** | `directory_info.cpp/.h`, `kernel_file.cpp` | **real, tested** | `FILE_DIRECTORY_INFORMATION` records for a directory handle, walked one entry per call ending in `STATUS_NO_MORE_FILES`. `next_entry_offset` is the part that matters — a walker follows it until it reads zero — so records are 8-byte aligned, the last terminates with 0, and a record that does not fit writes **nothing**. Timestamps are left zero rather than invented: a title sorting saves by date would order them by a number this runtime made up. A directory handle carries **no `FILE*`**; every byte-transfer path answers `STATUS_INVALID_DEVICE_REQUEST` instead of dereferencing null. `tests/test_directory_info.cpp` |
| **HLE D3D** | `hle_d3d.cpp` | **partial** | The native-override seam for the guest D3D layer, with a per-frame call census carrying call-site provenance (channel `hle`). Overriding **works** now -- it did not before `tools/prepare_overrides.py`, and a strong override linked cleanly while never being entered. ~60 guest functions are wrapped so far, all for instrumentation (census, worker-queue watchpoint, shader argument scan); none replaces guest behaviour **First function read at the seam**: `SetTexture` (0x82220858) is wrapped -- contract in `docs/d3d-seam.md` §1b, super-call keeps the guest body authoritative -- and its per-frame slot table is printed next to the renderer's `frame texture bases` line so the API's account and the PM4-derived one can be diffed. They agree in the movie phase |
| **GPU** | `vd_null_gpu.cpp` | **command processor** | Consumes the ring, follows indirect buffers, and executes TYPE0 register writes, `EVENT_WRITE_SHD` fences, `EVENT_WRITE_ZPD` occlusion reports, `WAIT_REG_MEM`, `INTERRUPT` (dispatched per CPU) and **predication** via bin mask/select. It rasterises nothing itself: it accumulates each frame's `DRAW_INDX`/`_2` with the register state live at that draw and hands the ordered list to the guest-draw backend at the swap — unconditionally, no knob. Vblank at 60 Hz (`GEARS_NO_VBLANK=1` disables). `GEARS_CP_STALL_MS=N` blocks the CP thread for N ms at the first swap doing nothing else — the control arm for "did our host-side work perturb the guest?"; measured, a 20 s stall costs throughput only and induces no guest error path (issue #26) |
| **Guest-draw backend** | `runtime/gpu_draw.cpp` (the frame function: per-draw preparation, command recording, the presented-surface choice and the frame report) plus, split out of it, `gpu_draw_renderer.h`/`gpu_draw_prepared.h` (the types), `gpu_draw_formats.*` (Xenos state -> Vulkan), `gpu_draw_pixels.*` (guest number formats), `gpu_draw_targets.*` (the render-target cache) and `gpu_draw_resolve.cpp` (its two resolve dispatches), `gpu_draw_pipelines.*` (pipeline + layout caches), `gpu_draw_shaders.*` (the shader translation cache, and where a native pass is substituted), `gpu_draw_arena.*` (the per-draw uniform/index arena), `gpu_draw_uniforms.*` (the five constant blocks and their cache), `gpu_draw_indices.*` (index read/widen/quad-list expansion), `gpu_draw_descriptors.*` (the four descriptor sets and their per-frame cache), `gpu_draw_census.*` (what the frame contained, and the report lines that consume it), `gpu_draw_resolve_decode.*` (reading a kCopy draw's registers into a resolve) — the split out of the frame function is verified **live**, not only in replay: a 150 s headless run rendered 3205 frames with no new error and the same per-frame cost breakdown, `gpu_draw_probe.*` (the FRAME_STEP and PIXEL_TRACE probes, and the pipeline-statistics/DIAG table), `gpu_draw_textures.*` (the texture uploader) and `gpu_draw_untile.*` (the EDRAM-tiling collapse); `runtime/gpu_draw_xlate.cpp` (Xenos→SPIR-V + Modification + SystemConstants + the resolve compute shaders, isolated static lib), `runtime/frame_capture.cpp` | **real, verified on real data** | **Renders the guest's own frames, live, including the deferred in-game scene.** Persistent renderer (`RendererPersistent`) driving ~30 fps; per-draw shader **Modification** (the interpolator mask — a zero mask shades every pixel black while rasterising perfectly), guest textures from fetch constants, guest viewport/scissor/output-merger state, `kQuadList` expansion and a `kRectangleList` **geometry shader**. **Render-target cache**: one host colour target per EDRAM `RB_COLOR_INFO` base, every draw routed to its surface; `RB_MODECONTROL.edram_mode` honoured (`kCopy` is a RESOLVE, not geometry; the pixel shader runs **only** for `kColorDepth`). **Guest memory**: the SSBO spans the full 512 MiB physical window — it was 64 MiB, and an Act 1 frame fetches to 237 MiB, so 606 of 722 draws read ZERO and every primitive collapsed at clipping (`catalog.py show 30`) — while uploading only the ranges the frame fetches (764 KiB in 25 spans). **Clears are the guest's**: they ride on copy draws, so depth is cleared once per predicated TILE with `RB_DEPTH_CLEAR` decoded per depth format (`catalog.py show 31`, `34`). **Tile assembly**: a resolve destination is a REGION OF A TEXTURE — the guest folds a tile's row offset into `RB_COPY_DEST_BASE`, so `0xc2e0000` is row 512 of the texture at `0xbde0000` (`catalog.py show 32`). **Resolves are compute dispatches, not blits**: colour applies `copy_dest_exp_bias` (this title resolves HDR with bias −3, so ignoring it left the tonemap's input 8× too bright — `catalog.py show 33`) and `copy_dest_swap`; depth writes what the guest's `k_24_8_FLOAT` fetch would produce into an R32_SFLOAT target (`catalog.py show 35`). **Measured on a captured Act 1 frame**: 722/737 draws issued, 0 skipped; 12 colour + 3 depth resolves; 54 bindings served by a resolve target, **0 by a stub**; 0.0% of pixels saturated. Knobs are **control arms and dumps, never fixes**: `GEARS_DRAW_STATS`, `GEARS_DRAW_DIAG=<tsv>` (the per-draw verdict table), `GEARS_DRAW_RESOLVE_DUMP`, `GEARS_DRAW_RESOLVE_COMPUTE`/`_BLIT`/`_SCALE`/`_NOSWAP`, `GEARS_DRAW_ONLY[_BASE]`, `GEARS_DRAW_VDUMP=N` (indexed as the diag table's `draw` column), `GEARS_DRAW_NOTEX`, `GEARS_DRAW_NOBLEND`, `GEARS_DRAW_NODEPTH`, `GEARS_DRAW_DEPTH_CLEAR`, `GEARS_DRAW_VALIDATE`, `GEARS_DRAW_FRAME_DUMP=<path>` (frame capture)  **Frame cost, live, measured 2026-08-05 with the host runtime compiled at -O2 (`catalog.py show 59` -- it never was before, and every earlier number here was of a debug renderer)**: menus and movies render at **29.5 fps with 0 dropped frames**, 13-16 ms a frame. Act 1 gameplay, 743 draws a frame, renders at **14 fps** (53 ms) while the guest's own loop holds **29 fps** -- the render is on its own thread (`catalog.py show 56`), so the guest no longer waits for it. The same gameplay frame replayed OFFLINE costs 29 ms (draw loop 16 = modification derivation 5 + own state 2 + uniforms 3 + record 4 + prep 2; submit/wait 6; readback 7 on reported frames only), so roughly half the live cost is contention with the guest's threads, not renderer work. **Texture descriptor sets are shared between draws** keyed on the shader pair and the fetch constants behind each binding: 639 of 725 draws reuse an earlier draw's, and binding resolutions per frame fell 5224 -> 796. Next levers, in size: the live/offline contention gap (~24 ms), submit/wait pipelining (6 ms), modification derivation (5 ms). **Run-to-run spread is ~8 ms**, so a change smaller than that cannot be judged by comparing runs: use `GEARS_DRAW_AB_CENSUS=1` and `runtime/frame_ab.*`, which interleave the two arms frame by frame inside one run and refuse to report a difference smaller than the noise |
| **Render thread** | `runtime/render_thread.*` | **real, measured** | The frame's draw list is handed to a thread and the command processor returns, because rendering inside the guest's VdSwap paced the guest by our renderer: gameplay ran at 10.5 VdSwap fps against 29.9 in the menus, and recovered to 27.8-28.5 when the render moved off that thread (`catalog.py show 56`). A frame arriving while the renderer is busy is DROPPED and counted -- never queued. The thread is niced down: its work is the only work in the process that may be skipped, and the audio mixer's 187.5 Hz hand-off may not. Capture and measurement runs (`GEARS_DRAW_FRAME_COUNT>0`) still render in line, where the render IS the measurement |
| **Guest textures** | `runtime/gpu_draw_xlate.cpp` (`DecodeGuestTexture`, `DeriveSamplerState`), `runtime/gpu_draw_textures.cpp` (`TextureUploader::Upload`, `::GetSampler`, `TextureBinder::SelectView`) | **real, verified on real data** | Texture fetch constants (`0x4800 + fc*6`) are decoded into host images using **Xenia's own machinery** — `texture_util::GetSubresourcesFromFetchConstant` (extents, mip range), `GetGuestTextureLayout` (row pitch, slice strides), `texture_address::Tiled2D/Tiled3D` (the tiled address function), `FormatInfo` (block size). Endianness is an XOR on the source byte offset (`k8in16`→`^1`, `k8in32`→`^3`, `k16in32`→`^2`); the guest swizzle is composed with the host format's component order per `TextureCache::GuestToHostSwizzle` and applied through the `VkImageView` component mapping. Sampler state is the guest's too (filters, clamp modes, anisotropy from the fetch constant each sampler binding names). **Measured on scene frame 600**: 26 distinct fetch constants, 20 uploaded (1.5 MiB), **176 of 218 texture bindings (80.7%) served by real guest data**; format distribution `k_DXT4_5`×13, `k_DXT1`×7, `k_24_8_FLOAT`×2, `k_16_16`, `k_16_16_16_16_EXPAND`, `k_16_16_16_16_FLOAT`, `k_8_8_8_8` — all 2D, all tiled. **Decode verified independently**: `GEARS_DRAW_TEX_DUMP=1` + `tools/decode_bc.py` produce recognisable Gears world art from the decoded blobs. **The cache evicts**: entries are keyed on the fetch constant, which does not change when the guest overwrites the pixels at the same address, so each distinct texture's guest bytes are re-hashed once per frame and a changed one is retired (after the frame's fence, since recorded draws still reference it) and re-uploaded. Without it the startup movie -- new Y/U/V planes at three fixed addresses every frame -- was frozen at its first, black frame for the whole intro (`catalog.py show 53`). Gaps: base level only (no mip tails), `k_24_8_FLOAT`/`k_16_16_16_16_EXPAND` unmapped and counted |

## Where is X?

- *A draw's geometry vanished before rasterisation?* → check the **frame geometry reach** line first. A vertex fetch past the guest-memory SSBO mirror reads **zero**, so every vertex collapses to the origin and the whole primitive dies at clipping — which looks nothing like a memory bug and exactly like a transform bug. This cost the project the entire in-game world: the mirror was 64 MiB while an Act 1 frame fetches to 237 MiB (`catalog.py show 30`). The mirror now spans the full 512 MiB window and uploads only the ranges the frame fetches
- *Why does the game see zeros at an address?* → `import_variables.cpp` (variable imports start zeroed)
- *Why is a physical pointer valid at four addresses?* → `guest_memory.cpp`, `MapPhysicalAliases`
- *What decides an import traps vs runs?* → `implemented_imports.h` + `tools/gen_import_stubs.py`
- *Where does the picture come from?* → `vd_null_gpu.cpp` accumulates every DRAW_INDX/_2 of a frame and hands the ordered list to the whole-frame guest-draw backend (`runtime/gpu_draw.cpp`) at the swap. This is unconditional — not behind a knob — and produces a recognisable game image (99.8–100% non-black); `GEARS_DRAW_FRAME_AT`/`_COUNT` only bound *which* frames a capture or measurement run draws. General rendering is the HLE work in `docs/d3d-seam.md`
- *Why is a shader's output black even though it rasterises?* → the **shader modification**, not the shader. `Modification.interpolator_mask` decides which interpolators the VS exports and the PS reads; a zero mask (which `GetDefault*ShaderModification` gives you) makes every interpolant read as 0 while position and clipping stay perfect. Derive it per draw from the pair + `SQ_PROGRAM_CNTL`/`SQ_CONTEXT_MISC` (`DeriveShaderModifications`), and cache translations by **(hash, modification)**. Confirm with `GEARS_DRAW_STATS=1`: many fragment invocations + no pixels = shading, not rasterising
- *A draw contributed nothing — which stage did it die at?* → **do not guess, and do not A/B against a live run.** `GEARS_DRAW_DIAG=<path.tsv>` writes one row per issued draw joining what it *was* (EDRAM surface, `edram_mode`, primitive, shader hashes) with what it *did* (pipeline statistics: IA vertices, IA primitives, primitives after clip+cull, fragment invocations) and every piece of state that can silently zero it (depth test/write/func, colour mask, blend, viewport and scissor extents, `PA_CL_CLIP_CNTL`, `PA_SU_SC_MODE_CNTL`, `PA_CL_VTE_CNTL`, `PA_SC_WINDOW_OFFSET`, the raw viewport scale/offset). The `verdict` column names the stage directly: `no_primitive_assembled` / `killed_by_clip_or_cull` / `rasterised_no_fragment` / `depth_only_no_colour` / `colour_fully_masked` / `shaded`. Run it under `frame_replay` so it costs a second — this is how issue #30 and #31 were separated, after two earlier suspects had survived precisely because live runs were not comparable
- *How do I iterate on the renderer without a 200-second boot?* → capture once with `GEARS_DRAW_FRAME_DUMP=<path>` on a `tools/capture_gameplay_frame.sh` run, then replay with `scratch/build/runtime/frame_replay <capture>` as often as needed. See the tools table
- *Which frame should I capture?* → `GEARS_DRAW_FRAME_AT=N`. Loading frames carry 2–3 draws; the scene phase begins at frame **571** and holds 168–186 draws/frame. Profile any run by setting `GEARS_DRAW_FRAME_AT` beyond its length — one `guest-draw: frame N has M draws` line per frame
- *Why is a draw black / why did the driver crash on a shader?* → the output-merger state (`RB_COLOR_MASK`/`RB_BLENDCONTROL0`/`RB_DEPTHCONTROL`) and the texture descriptor set layout are **per draw and per shader**; hardcoding either is a defect, not a simplification. Bisect with `GEARS_DRAW_FRAME_STEP=N` (checkpoint images) + `GEARS_DRAW_FRAME_LIST=1` (per-draw census)
- *Why is the frame rate what it is?* → vblank pacing is faithful (~8 ms/wait on `0x30B004`) and must not be shortened; see `catalog.py show 16`
- *Where do I get Xenos shader/packet semantics?* → `extern/xenia` submodule (BSD-3 fork, pinned); see `docs/xenia-reuse.md`
- *How do I get a shader out of the game and into SPIR-V?* → `tools/shader_extract.py` then `scratch/build/tools/xenos_translate/xenos_translate`; layout in `docs/d3d-seam.md` §3
- *Which shaders does the title actually bind, and where?* → `GEARS_SHADER_CAPTURE=1` (PM4 sequencer loads), then `xenos_translate --raw` and `tools/compare_bound_shaders.py`; setters are `sub_82222B98` (vertex) / `sub_82222808` (pixel), see `catalog.py show 21`
- *Why doesn't captured microcode match the corpus?* → the title patches the vertex fetch into the instruction at bind time; `catalog.py show 22`
- *Why are Xenia's asserts off in `xenia_gpu/`?* → every vertex shader in this title has a zero vfetch stride; see the comment in `xenia_gpu/CMakeLists.txt`
- *About to believe a diagnostic's NEGATIVE result?* → **check the instrument could have produced a positive first.** This project has hit that four times in one session, and it is now the dominant failure mode: `find_addr_refs.py` scanned only one of the two address-building shapes; a vtable scan recognised commands by a slot the abstract case also occupies, so it could only ever print 0; `atomic_audit.py` computed its dataflow registers and never used them; and a probe capped at 4 reports concluded "the array is always empty" from 4 of **78,278** calls. Every one of those read as an answer. Feed the instrument a case that MUST produce a positive — `GEARS_ASAN_SELFTEST` in `runtime/main.cpp` is the shape to copy — and prefer a cap that reports the INTERESTING state over the first N
- *Looking for what references a guest address, and finding nothing?* → `tools/find_addr_refs.py` scans for BOTH shapes that build an address: `lis`+`addi` (computed into a register) and `lis`+`lwz/stw` (used directly as a load/store displacement). It recognised only the first until 2026-07-29, so any global whose only writer used the second read as having **no writers** — and a session was spent reasoning from that absence (`catalog.py show 45`). If a scan returns nothing, confirm the tool can see the shape you are looking for before believing it
- *A guest null-pointer read returned interesting garbage instead of faulting?* → guest address 0 is MAPPED. `kPhysicalAliases` in `guest_memory.cpp` includes the raw physical window `0x00000000`, so the console's whole 512 MiB is readable at address 0 and a null dereference reads live physical RAM. This makes null-pointer bugs **nondeterministic and misleading**: the same bug produced a 2.6 GB allocation when physical page 0 happened to hold `0xb0800000`, and vanished entirely when it happened to hold zeros. If a memory symptom moves when unrelated allocation patterns change, suspect this before believing any fix (`catalog.py show 45`)
- *A title is behaving as if a system service failed, and the symptom is nowhere near it?* → check what the runtime REFUSES. Every refusal in `xam_user.cpp` is locally defensible and collectively describes a console the title cannot use. `XamShowDeviceSelectorUI` sat in the no-system-UI list for months; refusing it meant the title never obtained a storage device, and it surfaced sixty seconds later and four subsystems away as a 2.6 GB allocation and a segfault (`catalog.py show 45`). A PC port can always answer that one — there is exactly one place saves go
- *Which guest functions led to a call, when the chain is reached through function pointers?* → `runtime/guest_backtrace.cpp`. Walks the guest stack: the back chain is at `0(r1)` and the return address into each caller is `back_chain - 8` (the slot `__savegprlr_N` writes with `stw r12,-8(r1)`). Bounded to the current 1 MiB stack and to strictly-increasing frames, because most of the 4 GiB guest space is reserved-not-committed and a stray read faults. This replaced probing one `sub_X` per level, which cost **a full run per frame of the chain**; it named twelve frames in one line. Validate any such instrument before believing it — frame 0 must match a link register known independently, and the outermost frame should land just past the image entry `0x82612bf0`
- *A guest call is returning the wrong thing and the arguments look fine?* → **count the parameters, and check whether the one you want is on the STACK.** This ABI passes the first eight integer arguments in r3..r10 and the rest in the caller's parameter save area at `r1+0x14` in eight-byte slots, so the ninth is at `r1+84`. `runtime/guest_stack_argument.h` reads them by index. This cost a full day: `XamContentCreateEx` has NINE parameters and our implementation documented seven, reading the overlapped block out of r9 — which is `cacheSize`, and which the title's own wrapper zeroes right after spilling the real overlapped to the stack. We therefore saw no overlapped, completed the call synchronously, and returned plain success; the checkpoint loader requires `ERROR_IO_PENDING` and, given success, reported success having loaded nothing. The visible symptom was a use-after-free four subsystems away, in the title's own linker (`catalog.py show 45`). **A syscall that returns success carrying no data is the most expensive shape a host shim can have** — the title believes it worked and the crash lands nowhere near the lie
- *The process died and the log just STOPS?* → `runtime/fault_report.cpp` reports it: signal, the faulting address classified against the guest mapping, and a host backtrace — which IS the guest call chain, because recompiled functions are host functions named `sub_82xxxxxx`. It chains to the previous disposition so the core dump and exit status are unchanged, and every thread gets an alternate signal stack (guest threads in `kernel_thread.cpp`) since a handler with nowhere to run reports nothing. **Six consecutive runs of the #45 repro dumped core in silence before this existed**, and every hypothesis they were meant to test was judged against a log that merely stopped. Two traps to know: the mapping base is ASLR-randomised, so a "that was a host pointer" verdict is only meaningful read against the base printed in the SAME run; and the installer must not take the mapping as an argument — an earlier one was called with `gears::Memory()` before `SetMemory()` and killed the process on its first line, costing three 280-second runs whose logs held ONE line each. **Check `wc -l` on a log before reading it**
- *An indirect call jumped into host memory, or the title branched somewhere impossible?* → `runtime/guest_indirect_call.h` takes over `PPC_CALL_INDIRECT_FUNC` (`ppc_context.h` leaves it `#ifndef`-guarded for exactly this) and validates all **29,190** call sites: inside the code section, four-byte aligned, non-null table entry. The recompiler's default is a raw table index with NO validation, so a stale vtable slot reads a host function pointer out of whatever lies at that offset and calls it — which is how #45 presented as a SIGSEGV two gigabytes below the guest mapping with nothing to say which pointer was bad. On failure it names the target, thread, guest stack, registers, and the words the pointers point at, then aborts. It must be force-included AFTER `ppc_mmio.h` and via `SHELL:` in CMake, or CMake de-duplicates the repeated `-include` token and the second header arrives as a bare input file
- *How do I reproduce anything on the checkpoint/campaign path?* → `tools/run_to_checkpoint.sh <log>`. Drives the title headless from boot through its own menus into the campaign with a recorded `GEARS_INPUT_SCRIPT`. Without the script the title simply sits in the main menu, so a plain run never reaches the interesting code at all
- *What has already been ruled out for the current crash?* → `catalog.py show 1`
- *Why won't my gdb watchpoint fire?* → `catalog.py show 5` (physical aliasing / stale addresses)
- *Why do registers look wrong at a watchpoint?* → `catalog.py show 6`
- *Why is my native override never entered?* → clang folds intra-TU calls through the weak alias; run `tools/prepare_overrides.py`, and note `sub_X` is C++-mangled, not `extern "C"`. Details in `catalog.py show 16`

## Current state

Boots, loads its own packages, plays the startup movies, walks its own menus
under a controller, reaches **Act 1 gameplay**, renders the guest's frames at
~30 fps, and **responds to the player** — holding the left stick moves the camera
through the level, proven against a no-input control arm (172 of 173 frames
changed with the stick, 0 of 129 without; `catalog.py show 38`). The deferred in-game frame renders: whole (both predicated tiles),
correctly exposed (0.0% of pixels saturated), depth-tested and depth-lit.

**Not yet faithful**, each measured rather than guessed and tracked on
`docs/re-frontier.md`: the colour clear is still a diagnostic sentinel rather
than the guest's; the resolve ignores destination tiling and scaling; cull mode
is host-fixed to NONE; resolved depth is not quantised to the guest's float24
(one 20-bit ULP); and one host depth image serves four `RB_DEPTH_INFO` bases —
measured as ~1% of draws, since both major surfaces genuinely share base 0x0.

**The renderer is debugged through instruments, not screenshots**, and that is
not a stylistic preference. Six defects this session produced output that looked
plausible: a descriptor pool sized from a list that was still empty, a dispatch
borrowing descriptor sets of the wrong layout, a pool undersized for two set
types, an `OpImageFetch` missing its `Lod` operand, a `VDUMP` index that meant a
different draw from the diagnostic table's, and a census recording the previous
draw's shader hash. Each was caught by a reading that could not have come from a
healthy system — most often a resolve target reading exactly `0.000`. **The dump
that catches them had itself to be fixed first**: it read every target as
half-float and so reported `0.000` for an R32_SFLOAT depth target regardless of
content. An instrument that cannot tell "wrote nothing" from "I am reading it
wrong" is worse than none.

The heap leak that capped runs at ~160 s is fixed (issue #17), as is the
intermittent SIGSEGV at frame ~21840 (issue #18): peak use plateaus at 192/194
MiB and the title runs past frame 25000 at ~30 fps.

## Standing hazards

Several of these have each cost more than one session:

- **Decompiler output is fiction** wherever Ghidra failed to rebuild a function,
  because `DecompXbox.py` stubs the save/restore helper ranges -- and `Disasm.py`
  silently degrades to a byte dump in exactly those places. Check anything
  suspicious with `tools/ppcdis.py`, which decodes from the image directly.
  Five wrong conclusions have come from this, including two "established facts".
- **A negative result is only as good as the detector.** Ring lapping was
  recorded as ruled out twice on the strength of a check that could not fire,
  because the available-space calculation was masked. Before trusting a prior
  negative, confirm the test could have detected the thing.
- **Suspect this port before the title.** Most blockers so far have been defects
  here, not in the game: silently dropped switch cases, a 64-bit switch on a
  32-bit dispatch, an unlocked heap, an import-name comparison that never
  matched, a device register written in the wrong byte order, alias folding that
  made overrides no-ops, and a missing predicate bit that cost 70x frame rate.

A differential harness against Xenia was tried and **abandoned** -- it never
executed the title, and an unreliable oracle is worse than none. See
`catalog.py show 7`. Do not resume it. This is unrelated to `extern/xenia`,
which is used as a *reference for hardware contracts* and has been good for
exactly that.
