# Codemap

Orientation map for the GearsUE3 engine port. Consult this **before** starting work to find where
a subsystem lives and how far it actually got; update it in the **same commit**
that lands or changes a subsystem.

Status vocabulary — deliberately narrow, so it cannot flatter the project:

| Status | Meaning |
|---|---|
| **real** | Implemented and verified against real data. Does what its name says. |
| **partial** | Genuinely implemented, but with known gaps. Gaps named. |
| **null** | Deliberately does nothing while presenting a working interface. Not a stub to be filled in later by accident — a *documented* absence. |
| **absent** | Not implemented. Traps loudly if called. |

| `tools/img_extent.py` | **Where the content is in a frame, measured so a threshold cannot invent the answer.** `sweep` reports the content bounding box at SIX luminance thresholds (0.002…0.10) plus a per-column mean-luminance profile, and refuses to report a single box; `compare` gives pixelwise identity, identity-under-red/blue-swap, mean absolute AND mean **signed** channel difference, because a constant signed offset is a brightness difference and not a geometric one. **Read a sweep this way**: a box that MOVES inward as the threshold rises is a bright subject inside a darker rendered frame; a box that HOLDS below full width at 0.002 is real geometry. | `runtime/guest_clock.{h,cpp}` | **The clock the guest reads, in one place** — mftb (via a `__ppc_set_time_base_source` hook in XenonRecomp's `ppc_context.h`), the `KeTimeStampBundle`, and `KeQuerySystemTime`. `GEARS_GUEST_CLOCK_STEP_NS=<n>` makes it advance a fixed step per presented frame instead of tracking real time, so the simulation becomes a function of the input schedule — the prerequisite for any live cross-emulator comparison (catalog #84: without it the title reaches 17.7% identical pixels against **itself** by frame 1200). **Status: the plumbing is real and the guest runs happily on a synthetic clock, but stepping at VdSwap DEADLOCKS the title at boot** (0 frames against 9 for the control) because it spins in guest code waiting for time before its first present. `GEARS_GUEST_CLOCK_TRIGGER` picks what advances it: `present` (deadlocks — the boot spin waits on TIME, proved by a host-paced-vblank arm that still hit 0 frames), `vblank` (host-paced control arm — boots and stays **alive**, but real time is in the clock), `vblank-freerun` (**freezes the picture**: presents continue to frame 10,800 but every frame from ~2,700 is bit-identical to the last, where the real clock's are 21–34%). **The freeze makes the determinism control pass perfectly on a still image** — never quote a cross-run identity number without the liveness check (instrument I027). | `tools/frame_replay/` + `runtime/frame_capture.cpp` | **The renderer's instrument — reach for this before any renderer hypothesis.** `GEARS_DRAW_FRAME_DUMP=<path>` records one frame's whole draw stream (per-draw register snapshots, deduplicated microcode, the non-zero guest pages); `frame_replay <capture>` re-renders it offline in **~550 ms with no guest**. **A capture is not self-contained**: it stores renderer configuration as it was when recorded, and `frame_replay` overrides the guest-memory mirror with the runtime's current value and warns when they differ — a capture from before the mirror was raised replayed with 606 of 722 draws collapsed and produced a plausible, wrong picture (`catalog.py show 57`). ## Where is X?

- *A draw's geometry vanished before rasterisation?* → check the **frame geometry reach** line first. A vertex fetch past the guest-memory SSBO mirror reads **zero**, so every vertex collapses to the origin and the whole primitive dies at clipping — which looks nothing like a memory bug and exactly like a transform bug. This cost the project the entire in-game world: the mirror was 64 MiB while an Act 1 frame fetches to 237 MiB (`catalog.py show 30`). The mirror now spans the full 512 MiB window and uploads only the ranges the frame fetches
- *A draw covers far less of the screen than its vertices span, or a full-screen fill vanishes entirely?* → **`PA_CL_CLIP_CNTL.clip_disable`**, which 61 of `walk_gameplay.gfr`'s 552 draws set. Disabled clipping is emulated with a host viewport LARGER than the render target (Xenia returns up to 8192x8192) plus an `ndc_scale` that rescales the vertices into it, and with `depthClampEnable` so a primitive whose Z is a hair outside [0,1] is clamped rather than clipped away. BOTH halves are required and each failed separately here (`catalog.py show 91`): the viewport was clamped to the target while the shader kept rescaling for 8192, which shrank every such draw by the ratio between them (a 640x360 depth+stencil fill wrote 100x32), and `depthClampEnable` was never set, which killed two full-screen fills written at z = -3.7e-09 outright. Measure it with `GEARS_DRAW_DEPTH_DUMP=<diag>`, not with the diag table: a depth-only draw has no fragment stage, so its coverage never appears as a fragment count
- *What does the DEPTH buffer actually hold at draw N?* → `GEARS_DRAW_DEPTH_DUMP=<diag>[,…]`, which writes `depth_after_diag<N>.npy` (float depth in channel 0, the raw stencil byte in channel 1) and prints depth min/max/mean, the most common depth with its share, and every stencil value present with its count. Every earlier answer to this was INDIRECT — through the aliasing pass's encode and an 8888 unpack — and one was a test that could not have failed, because the value it looked for was also the value a far fill writes
- *Why does the game see zeros at an address?* → `import_variables.cpp` (variable imports start zeroed)
- *Why is a physical pointer valid at four addresses?* → `guest_memory.cpp`, `MapPhysicalAliases`
- *What decides an import traps vs runs?* → `implemented_imports.h` + `tools/gen_import_stubs.py`
- *Where does the picture come from?* → `vd_null_gpu.cpp` accumulates every DRAW_INDX/_2 of a frame and hands the ordered list to the whole-frame guest-draw backend (`runtime/gpu_draw.cpp`) at the swap. This is unconditional — not behind a knob — and produces a recognisable game image (99.8–100% non-black); `GEARS_DRAW_FRAME_AT`/`_COUNT` only bound *which* frames a capture or measurement run draws. General rendering is the HLE work in `docs/d3d-seam.md`
- *How can an external debugger drive and inspect the live port?* → `runtime/debug_http.cpp` on `127.0.0.1:32123`: atomic controller replacement, guest/input/render status, and an on-demand PPM from the renderer's readback path. `runtime/frame_probe_capture.h` lets that explicit diagnostic render one complete frame even while a capture selector is held, without opening the selector, consuming `DRAW_FRAME_COUNT`, or emitting report artifacts. See `docs/interactive-debug.md`
- *Why is a shader's output black even though it rasterises?* → the **shader modification**, not the shader. `Modification.interpolator_mask` decides which interpolators the VS exports and the PS reads; a zero mask (which `GetDefault*ShaderModification` gives you) makes every interpolant read as 0 while position and clipping stay perfect. Derive it per draw from the pair + `SQ_PROGRAM_CNTL`/`SQ_CONTEXT_MISC` (`DeriveShaderModifications`), and cache translations by **(hash, modification)**. Confirm with `GEARS_DRAW_STATS=1`: many fragment invocations + no pixels = shading, not rasterising
- *A draw contributed nothing — which stage did it die at?* → **do not guess, and do not A/B against a live run.** `GEARS_DRAW_DIAG=<path.tsv>` writes one row per issued draw joining what it *was* (EDRAM surface, `edram_mode`, primitive, shader hashes) with what it *did* (pipeline statistics: IA vertices, IA primitives, primitives after clip+cull, fragment invocations) and every piece of state that can silently zero it (depth test/write/func, colour mask, blend, viewport and scissor extents, `PA_CL_CLIP_CNTL`, `PA_SU_SC_MODE_CNTL`, `PA_CL_VTE_CNTL`, `PA_SC_WINDOW_OFFSET`, the raw viewport scale/offset). The `verdict` column names the stage directly: `no_primitive_assembled` / `killed_by_clip_or_cull` / `rasterised_no_fragment` / `depth_only_no_colour` / `colour_fully_masked` / `shaded`. Run it under `frame_replay` so it costs a second — this is how issue #30 and #31 were separated, after two earlier suspects had survived precisely because live runs were not comparable
- *How do I iterate on the renderer without a 200-second boot?* → capture once with `GEARS_DRAW_FRAME_DUMP=<path>` on a `tools/capture_gameplay_frame.sh` run, then replay with `scratch/build/runtime/frame_replay <capture>` as often as needed. See the tools table
- *Which frame should I capture?* → `GEARS_DRAW_FRAME_AT=N`. Loading frames carry 2–3 draws; the scene phase begins at frame **571** and holds 168–186 draws/frame. Profile any run by setting `GEARS_DRAW_FRAME_AT` beyond its length — one `guest-draw: frame N has M draws` line per frame
- *Why is a draw black / why did the driver crash on a shader?* → the output-merger state (`RB_COLOR_MASK`/`RB_BLENDCONTROL0`/`RB_DEPTHCONTROL`) and the texture descriptor set layout are **per draw and per shader**; hardcoding either is a defect, not a simplification. Bisect with `GEARS_DRAW_FRAME_STEP=N` (checkpoint images) + `GEARS_DRAW_FRAME_LIST=1` (per-draw census)
- *Why is the frame rate what it is?* → treat title production and renderer throughput separately. First make Gears 1 stable and fast enough at its faithful cadence: `frame_queue.*` bounds stale-frame latency, while the measured warm 743-draw renderer is about 44 ms (about 34 ms in the flat draw loop). Only after the engine and compatibility paths are sound, add the last-priority per-revision 60 fps game override; rendering-disabled Gears 1 remains near 30 fps, so that override needs an evidenced semantic timing seam rather than a faster guest clock or vblank.
- *How is a disc matched to generated code?* → `tools/title_identity.py` binds the local disc, exact XEX, and normalized image through XenonRecomp's checked `xex-inspect` schema. XenonRecomp emits those exact executable digests into the ignored module's `ppc_config.h`; `runtime/title_executable.*` performs one checked load and hashes the executable, and `runtime/generated_title_profile.*` resolves the linked identity before any guest or save state activates. The remaining provisioning gap is one content-addressed receipt/orchestrator, not runtime exact-build enforcement.
- *What counts as support for another Gears title?* → `tools/title_conformance.py` requires exact-build evidence per gate. Gears 2, Gears 3, and Judgment cannot cite Xenia as their oracle; recognition, UE3 lineage, and a compiling shared engine are not compatibility evidence.
- *Where do I get Xenos shader/packet semantics?* → `extern/xenia` submodule (BSD-3 fork, pinned); see `docs/xenia-reuse.md`
- *How do I get a shader out of the game and into SPIR-V?* → `tools/shader_extract.py` then `scratch/build/tools/xenos_translate/xenos_translate`; layout in `docs/d3d-seam.md` §3
- *Which shaders does the title actually bind, and where?* → `GEARS_SHADER_CAPTURE=1` (PM4 sequencer loads), then `xenos_translate --raw` and `tools/compare_bound_shaders.py`; setters are `sub_82222B98` (vertex) / `sub_82222808` (pixel), see `catalog.py show 21`
- *Why doesn't captured microcode match the corpus?* → the title patches the vertex fetch into the instruction at bind time; `catalog.py show 22`
- *Why are Xenia's asserts off in `xenia_gpu/`?* → every vertex shader in this title has a zero vfetch stride; see the comment in `xenia_gpu/CMakeLists.txt`
- *About to believe a diagnostic's NEGATIVE result?* → **check the instrument could have produced a positive first.** This project has hit that four times in one session, and it is now the dominant failure mode: `find_addr_refs.py` scanned only one of the two address-building shapes; a vtable scan recognised commands by a slot the abstract case also occupies, so it could only ever print 0; `atomic_audit.py` computed its dataflow registers and never used them; and a probe capped at 4 reports concluded "the array is always empty" from 4 of **78,278** calls. Every one of those read as an answer. Feed the instrument a case that MUST produce a positive — `GEARS_ASAN_SELFTEST` in `runtime/main.cpp` is the shape to copy — and prefer a cap that reports the INTERESTING state over the first N
- *Looking for what references a guest address, and finding nothing?* → `tools/find_addr_refs.py` scans for BOTH shapes that build an address: `lis`+`addi` (computed into a register) and `lis`+`lwz/stw` (used directly as a load/store displacement). It recognised only the first until 2026-07-29, so any global whose only writer used the second read as having **no writers** — and a session was spent reasoning from that absence (`catalog.py show 45`). If a scan returns nothing, confirm the tool can see the shape you are looking for before believing it
- *A guest null-pointer read returned interesting garbage instead of faulting?* → guest address 0 is MAPPED. `kPhysicalAliases` in `guest_memory.cpp` includes the raw physical window `0x00000000`, so the console's whole 512 MiB is readable at address 0 and a null dereference reads live physical RAM. This makes null-pointer bugs **nondeterministic and misleading**: the same bug produced a 2.6 GB allocation when physical page 0 happened to hold `0xb0800000`, and vanished entirely when it happened to hold zeros. If a memory symptom moves when unrelated allocation patterns change, suspect this before believing any fix (`catalog.py show 45`)
- *A title is behaving as if a system service failed, and the symptom is nowhere near it?* → check what the runtime REFUSES. Every refusal in `xam_user.cpp` is locally defensible and collectively describes a console the title cannot use. `XamShowDeviceSelectorUI` sat in the no-system-UI list for months; refusing it meant the title never obtained a storage device, and it surfaced sixty seconds later and four subsystems away as a 2.6 GB allocation and a segfault (`catalog.py show 45`). A PC port can always answer that one — there is exactly one place saves go
- *Which guest functions led to a call, when the chain is reached through function pointers?* → `runtime/guest_backtrace.cpp`. Walks the guest stack: the back chain is at `0(r1)` and the return address into each caller is `back_chain - 8` (the slot `__savegprlr_N` writes with `stw r12,-8(r1)`). Bounded to the current 1 MiB stack and to strictly-increasing frames, because most of the 4 GiB guest space is reserved-not-committed and a stray read faults. This replaced probing one `sub_X` per level, which cost **a full run per frame of the chain**; it named twelve frames in one line. Validate any such instrument before believing it — frame 0 must match a link register known independently, and the outermost frame should land just past the image entry `0x82612bf0`
- *A guest call is returning the wrong thing and the arguments look fine?* → **count the parameters, and check whether the one you want is on the STACK.** This ABI passes the first eight integer arguments in r3..r10 and the rest in the caller's parameter save area at `r1+0x14` in eight-byte slots, so the ninth is at `r1+84`. `runtime/guest_stack_argument.h` reads them by index. This cost a full day: `XamContentCreateEx` has NINE parameters and our implementation documented seven, reading the overlapped block out of r9 — which is `cacheSize`, and which the title's own wrapper zeroes right after spilling the real overlapped to the stack. We therefore saw no overlapped, completed the call synchronously, and returned plain success; the checkpoint loader requires `ERROR_IO_PENDING` and, given success, reported success having loaded nothing. The visible symptom was a use-after-free four subsystems away, in the title's own linker (`catalog.py show 45`). **A syscall that returns success carrying no data is the most expensive shape a host shim can have** — the title believes it worked and the crash lands nowhere near the lie
- *The process died and the log just STOPS?* → `runtime/fault_report.cpp` reports it: signal, the faulting address classified against the guest mapping, and a host backtrace — which IS the guest call chain, because recompiled functions are host functions named `sub_82xxxxxx`. It chains to the previous disposition so the core dump and exit status are unchanged, and every thread gets an alternate signal stack (guest threads in `kernel_thread.cpp`) since a handler with nowhere to run reports nothing. **Six consecutive runs of the #45 repro dumped core in silence before this existed**, and every hypothesis they were meant to test was judged against a log that merely stopped. Two traps to know: the mapping base is ASLR-randomised, so a "that was a host pointer" verdict is only meaningful read against the base printed in the SAME run; and the installer must not take the mapping as an argument — an earlier one was called with `gears::Memory()` before `SetMemory()` and killed the process on its first line, costing three 280-second runs whose logs held ONE line each. **Check `wc -l` on a log before reading it**
- *An indirect call jumped into host memory, or the title branched somewhere impossible?* → `runtime/guest_indirect_call.h` takes over `PPC_CALL_INDIRECT_FUNC` (`ppc_context.h` leaves it `#ifndef`-guarded for exactly this) and validates all **29,190** call sites: inside the code section, four-byte aligned, non-null table entry. The recompiler's default is a raw table index with NO validation, so a stale vtable slot reads a host function pointer out of whatever lies at that offset and calls it — which is how #45 presented as a SIGSEGV two gigabytes below the guest mapping with nothing to say which pointer was bad. On failure it names the target, thread, guest stack, registers, and the words the pointers point at, then aborts. It must be force-included AFTER `ppc_mmio.h` and via `SHELL:` in CMake, or CMake de-duplicates the repeated `-include` token and the second header arrives as a bare input file
- *How do I reproduce anything on the checkpoint/campaign path?* → `tools/run_to_checkpoint.sh <log>`. Drives the title headless from boot through its own menus into the campaign with a recorded `GEARS_INPUT_SCRIPT`. Without the script the title simply sits in the main menu, so a plain run never reaches the interesting code at all
- *What has already been ruled out for the current crash?* → `catalog.py show 1`
- *Why won't my gdb watchpoint fire?* → `catalog.py show 5` (physical aliasing / stale addresses)
- *Why do registers look wrong at a watchpoint?* → `catalog.py show 6`
- *Why is my native override never entered?* → regenerate with the GearsUE3 XenonRecomp fork. It emits a weak noinline forwarder instead of a compiler alias, so same-translation-unit and cross-translation-unit calls both reach a strong override while `__imp__sub_X` remains callable. Details in `catalog.py show 16`

## Current state

Boots, loads its own packages, plays the startup movies, walks its own menus
under a controller, reaches **Act 1 gameplay**, renders the guest's frames at
~30 fps, and **responds to the player** — holding the left stick moves the camera
through the level, proven against a no-input control arm (172 of 173 frames
changed with the stick, 0 of 129 without; `catalog.py show 38`). The deferred in-game frame renders: whole (both predicated tiles),
correctly exposed (0.0% of pixels saturated), depth-tested and depth-lit.

The title screen's animated fire background is **pixel-exact against the
console at matched animation state** (0.00% of the fire pass's pixels differ;
`catalog.py show 88`): the pass is a procedural radial function of guest
constants that animate on guest time, so cross-emulator comparisons must pair
on animation STATE (the pass output or the camera constants), never frame
index — the console's own animation phase differs between oracle runs.

**Not yet faithful**, each measured rather than guessed and tracked on
`docs/re-frontier.md`: the colour clear is still a diagnostic sentinel rather
than the guest's; the resolve ignores destination tiling and scaling; cull mode
is host-fixed to NONE; resolved depth is not quantised to the guest's float24
(one 20-bit ULP); and one host depth image serves four `RB_DEPTH_INFO` bases —
measured as ~1% of draws, since both major surfaces genuinely share base 0x0.

**The renderer is debugged through instruments, not screenshots**, and that is
not a stylistic preference. Six defects this session produced output that looked
plausible: a descriptor pool sized from a list that was still empty, a dispatch
borrowing descriptor sets of the wrong layout, a pool undersized for two set
types, an `OpImageFetch` missing its `Lod` operand, a `VDUMP` index that meant a
different draw from the diagnostic table's, and a census recording the previous
draw's shader hash. Each was caught by a reading that could not have come from a
healthy system — most often a resolve target reading exactly `0.000`. **The dump
that catches them had itself to be fixed first**: it read every target as
half-float and so reported `0.000` for an R32_SFLOAT depth target regardless of
content. An instrument that cannot tell "wrote nothing" from "I am reading it
wrong" is worse than none.

The heap leak that capped runs at ~160 s is fixed (issue #17), as is the
intermittent SIGSEGV at frame ~21840 (issue #18): peak use plateaus at 192/194
MiB and the title runs past frame 25000 at ~30 fps.

## Standing hazards

Several of these have each cost more than one session:

- **Decompiler output is fiction** wherever Ghidra failed to rebuild a function,
  because `DecompXbox.py` stubs the save/restore helper ranges -- and `Disasm.py`
  silently degrades to a byte dump in exactly those places. Check anything
  suspicious with `tools/ppcdis.py`, which decodes from the image directly.
  Five wrong conclusions have come from this, including two "established facts".
- **Pair oracle artefacts by RUN, not by directory.** Two oracle runs reach
  different game moments (both emulators advance the guest by wall-clock delta,
  #84/#98), so frame N of one is not frame N of another — and nothing in either
  side's filenames records which run produced them. A capture gated against one
  run's camera, compared against a later run's resolve dumps, scored a 0.07
  correlation and cost a session before the timestamps gave it away. Check
  `stat` on both sides before quoting any cross-console number.
- **Before comparing two frames pixelwise, prove they are the SAME PICTURE — with
  a positive control.** A structural pairing (same pass, same camera constants,
  same frame index) does not imply the same rendered scene: a camera match to a
  view-projection distance of 3.77 scored a log-luminance correlation of 0.07
  against the console where a pair that genuinely agrees scores 0.93. Two wrong
  conclusions were published from that pair in one session. The correlation
  number means nothing on its own — always run the control, and search flips and
  shifts, because a misalignment and a different moment look identical without
  it. `tools/front_buffer_percentiles.py` gates on this and refuses. **A presence
  check ("ours is identically zero, theirs is not") is exempt** — it needs no
  moment match, and is often the only thing an unpaired capture can support.
- **A bounding box at ONE luminance threshold is not a measurement of geometry.**
  Over a dark scene it traces the LIT SUBJECT, not the rendered extent, so the
  same picture reads "inset" at 0.02 and "full width" at 0.002 -- and quoting
  boxes taken at different thresholds, on images of different brightness, as if
  they contradicted each other is what kept catalog #86 alive for six rounds
  after it had already been falsified once for this exact reason. Use
  `tools/img_extent.py sweep`, which reports six thresholds and says whether the
  box MOVES (a subject) or HOLDS (geometry). A darker frame at a fixed threshold
  has a smaller box; that is #62's brightness defect, not a geometry one.
- **Never conclude a defect from our side's numbers alone.** Measure the
  reference's DISTRIBUTION of the same quantity first. Three inferences
  collapsed on this in one session: post-clip primitive counts (235 against
  21,296 became 21,111 against 21,296 once the cameras matched), the shadow
  atlas region (framed as us writing where we should not, when it is a clear we
  do not perform), and clear-quad fragments (57 of the console's 59 such draws
  also produce none). `GEARS_ORACLE_PRIM_STATS` gives per-draw counts off the
  reference in about 90 seconds; there is no excuse for skipping it.
- **Fragment invocations are aggregate work, not unique pixel coverage.** In
  chapter 45, three shadow-atlas draws match the oracle's assembled primitive,
  post-clip primitive and fragment-invocation counts exactly (one differs by six
  invocations), yet the 10,932-vertex tile stores only 13,491 non-clear native
  pixels against 31,618 oracle pixels. Their complete raw index/fetch buffers,
  transform and pixel constants, tiled DXT1 source bytes, effective sampler
  state, and translated VS/PS SPIR-V also match. Use an actual uploaded-texel or
  spatial post-VS/raster instrument before calling equal pipeline counts equal
  geometry (`docs/issues/0109-*`).
- **Never compare the two emulators on anything a frame index, a draw ordinal
  or a content predicate selected.** All three have been tried and all three
  silently compared different moments of the game, because both sides advance
  the guest by wall-clock delta. It cost catalog #91 several sessions: our
  shadow-volume draws looked catastrophic, keeping 235 primitives of 54,352
  against the console's 21,296, until the frames were joined on the
  VIEW-PROJECTION (`c230..c233`, guest data both sides carry) instead -- at
  which point two independent runs came out at 21,111 and 21,224, within 1%.
  `tools/camera_match.py` finds the frame and refuses when none is close.
- **A negative result is only as good as the detector.** Ring lapping was
  recorded as ruled out twice on the strength of a check that could not fire,
  because the available-space calculation was masked. Before trusting a prior
  negative, confirm the test could have detected the thing.
- **Suspect this port before the title.** Most blockers so far have been defects
  here, not in the game: silently dropped switch cases, a 64-bit switch on a
  32-bit dispatch, an unlocked heap, an import-name comparison that never
  matched, a device register written in the wrong byte order, alias folding that
  made overrides no-ops, and a missing predicate bit that cost 70x frame rate.

**The Xenia oracle RUNS the title, headless** (`tools/xenia_oracle`, claim
C013): a windowless emulator built on the `extern/xenia` fork, driven by a
scripted pad, writing frames as PNGs. `tools/oracle_compare.sh` runs it and our
runtime on the same walk. Its limit is that the two sides reach a *different
game moment*, so every colour metric taken across them compares content as much
as rendering.

The fix for that limit -- replaying ONE captured frame through Xenia
(`tools/gfr_to_xtr.py` → `xenia-gpu-vulkan-trace-dump`) -- **now works, for a
named resolve rather than for the frame's final composite**.

`tools/gfr_trace_plan.py` owns trace selection separately from binary encoding.
`--checkpoint-copy RESOLVE:PREFIX` executes exactly `PREFIX` recorded draw
items, then appends that capture's real colour or depth resolve. This exposes
intermediate EDRAM through Xenia's shipping copy implementation without
mislabeling a truncated frame as complete, and its self-test rejects prefixes
after the selected resolve. **Its pixel content is currently DISTRUSTED:** on
the chapter-45 target, a forced-white shader with depth/stencil disabled produced
147,870 fragment invocations while the selected raw resolve remained zero.
Therefore the former claim that the first cross-renderer difference is after
draw 743 is withdrawn (C066, I051, I054). The complete C400 handoff still differs;
localising it requires a checkpoint readback that first passes this positive
control. The all-mip upload probe has separately ruled out authored mip bytes:
all 11 levels of all three target textures match Xenia exactly.

`--present resolve:N` points the swap at the Nth resolve (numbered as the fork's
own `IssueCopy` log numbers them) and truncates playback to end there. On
`bright.gfr`, `--present resolve:0` renders tile 1 of the scene from our own
capture: a lit brick wall, three windows, a blown-out courtyard. That is the
per-draw ground truth `catalog.py show 77` had been blocked on.

What does NOT work is `--present frame`, and the reason is measured (claim
C020): resolves DO reach shared memory in playback, but the frame's LATE
resolves write zeros over the early ones, so the final composite is empty by the
time the swap reads it. **Xenia's own captured trace fails identically**, resolve
for resolve, so this is Xenia trace playback and not our converter. Probe it with
`GEARS_PROBE_AFTER_RESOLVE=1` (instrument I022) -- `--gears_probe_front_buffer`
alone (I014) only samples at the swap and reports a false negative for every
destination a later resolve has since emptied.

Both sides now snapshot **per resolve**: `GEARS_DRAW_RESOLVE_DUMP_EACH=1` on
ours, `GEARS_PROBE_AFTER_RESOLVE=1` on the oracle's, and
`tools/resolve_pair.py <capture.gfr> <ours.log> <oracle.log>` pairs all eighteen
of `bright.gfr`'s copy draws. **Pair by DRAW INDEX, never by position** — our
renderer executes 14 of the 18, so position-pairing compares unrelated buffers;
the tool refuses when the counts disagree. It also labels the classes that say
nothing (the oracle's own emptied late resolves). **The depth resolves are no
longer among them** -- the per-resolve snapshot covers depth copies as of
2026-08-11 (`catalog.py show 90`).

`--regs delta` emits only the registers that changed since the previous draw
(393x fewer writes); more faithful to a real command stream, and measured NOT to
be the cause of the black composite.

The much older CPU-side differential harness against Xenia -- per-instruction
PPC tracing -- was tried and **abandoned** before any of the above; see
`catalog.py show 7`. Do not resume that one. Both are separate from
`extern/xenia` being used as a *reference for hardware contracts*, which it has
been good for throughout.

### Current texture-upload discriminator

`runtime/gpu_draw_vertexfetch.cpp` reports both the raw guest texture hash and
the actual `DecodeGuestTexture` upload-vector hash for selected draws. The
oracle fork's `vulkan_texture_cache.*` counterpart reads back the texture-load
compute output after its compute-to-transfer barrier and reports an explicit
zero-match negative. On issue #109 both shipping paths produced the same 32
canonical BC1 bytes (`683FAB1B2803B4D0`), so texture upload is covered and the
remaining shadow-atlas frontier is spatial post-VS/raster output.
